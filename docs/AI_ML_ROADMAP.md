# Роадмап AI/ML-части AlfaLearn

Дата: 11 ноября 2026 года. Владелец AI/ML-части — пользователь; Telegram-скелет разрабатывает другой участник команды.

Твоя цель — подготовить данные «Альфа-Курса», сделать проверяемые поиск, ответы и рекомендации и передать их боту как Python-модуль. Обучение своей нейросети на первом этапе не требуется.

Роадмап фиксирует исходный план и примеры. Для текущего состава AI/ML-модуля, порядка запуска и результатов используй [локальную приёмку](ai/LOCAL_ACCEPTANCE.md). Контракт для приложения описан в [инструкции интеграции](ai/INTEGRATION.md).

## 1. Что уже есть и что предстоит выбрать

Подтверждено пользователем после восстановления: PostgreSQL работает, таблиц 62; `Articles` — 855 строк, `Courses` — 37, `Lessons` — 508, `Podcasts` — 8. Adminer открыт. Это не заменяет проверку содержимого и прав доступа.

В локальном checkout на момент подготовки есть `AGENTS.md`, `docs/source/` и `compose.restore.yaml`; Python-кода бота и AI-модулей здесь пока нет. Код друга может находиться в другой ветке или еще не быть отправлен на сервер. Не создавай второй backend поверх его структуры: сначала согласуйте расположение общего Python-проекта.

Предлагаемый стек:

| Компонент | Назначение | Решение |
| --- | --- | --- |
| Python 3.12, uv | Язык, окружение, зависимости | Стартовая рекомендация; согласовать с ботом |
| psycopg 3 | Чтение восстановленной исходной БД | Только ETL, не обязательная зависимость работающего бота |
| BeautifulSoup4, lxml | Очистка HTML | Подготовка корпуса |
| Pydantic | Контракты данных и валидация | Общие схемы с backend |
| Sentence Transformers | Локальные embeddings | Первая версия поиска |
| `intfloat/multilingual-e5-base` | Стартовая embedding-модель | Кандидат, качество еще не измерено |
| Qdrant, qdrant-client | Индекс и поиск с фильтрами | Выбранное направление |
| LLM API и SDK провайдера | Ответы, уточнения, извлечение параметров | Модель и провайдер еще не выбраны |
| pytest, pytest-asyncio, Ruff | Проверки кода | Общие инструменты команды |
| Pydantic AI / LlamaIndex | Дополнительные обертки | Не обязательны для MVP |

SQLite, Telegram, расписание и доставка напоминаний — часть приложения. Твой модуль получает профиль и контекст, возвращает ответ либо предложение действия. Он не должен самостоятельно управлять Telegram-токеном и расписанием.

## 2. Границы ответственности и договор с другом

| Ты | Друг / backend | Вместе |
| --- | --- | --- |
| ETL, очистка, chunking | Telegram handlers, кнопки, команды | Формат запросов и ответов |
| Embeddings, Qdrant, retrieval | Хранение пользователя и истории | Контекст бизнеса и приватность |
| Ответы, рекомендации, уточнения | Выполнение действий, планировщик | Политика доступности материалов |
| Извлечение намерения напоминания | Запись, изменение, отмена, отправка | Подтверждение и ошибки действий |
| Набор проверок, метрики, эксперименты | Docker запуска приложения | Сквозная демонстрация |

Сразу договоритесь о следующих вещах:

1. Общий язык и версия Python, один ли `pyproject.toml` у backend.
2. Где твой пакет: предлагается `backend/alfa_ai/`, но путь можно поменять под существующий код.
3. Сначала Python-вызов внутри одного приложения; отдельный HTTP AI-сервис не нужен, пока нет причины его выделять.
4. Какие поля профиля и сколько истории тебе передают; никаких «модель сама прочитает всю SQLite».
5. Кто проверяет права и выполняет действия. Правило доступа нельзя оставить только в prompt.
6. Как бот показывает `clarify`, `no_answer`, `error` и ссылки.

Минимальные интерфейсы первой версии:

```python
def search_materials(query: str, limit: int = 5) -> list[SearchHit]: ...

async def answer(request: AIRequest) -> AIResponse: ...
```

Это будущие сигнатуры. У `AIRequest` нужны `query`, переданный профиль, ограниченная история, время и часовой пояс для временных намерений. `user_id` нужен для изоляции/журналирования, но обычно не нужен внешней LLM.

У `AIResponse` предусмотри:

```json
{
  "status": "answer",
  "text": "Ответ с обозначениями источников [S1]",
  "sources": [
    {"source_id": "S1", "document_id": "article:uuid", "title": "...", "url": "..."}
  ],
  "recommendations": [],
  "profile_patch": {},
  "proposed_action": null,
  "trace_id": "..."
}
```

Предлагаемые статусы: `answer`, `clarify`, `no_answer`, `action_proposal`, `error`. Это категории поведения, не доказательство уверенности модели.

## 5. Этап A — аудит данных

Где делать: Adminer → `alfa_course` → «SQL-команда», либо `psql`. Все запросы ниже только читают данные.

### A1. Посмотри реальные поля и справочник статусов

```sql
SELECT table_name, column_name, data_type
FROM information_schema.columns
WHERE table_schema = 'public'
  AND table_name IN (
    'Articles', 'ArticleEmbedItems', 'Glossary', 'GlossaryEmbedItems',
    'Courses', 'Lessons', 'LessonEmbedItems', 'ContentSettings'
  )
ORDER BY table_name, ordinal_position;

SELECT * FROM public."Statuses";
```

### A2. Посмотри сочетания признаков доступа статей

```sql
SELECT
    s."Title" AS status,
    a."IsDeleted", a."IsPublic", a."IsClosed",
    count(*) AS materials
FROM public."Articles" a
LEFT JOIN public."Statuses" s ON s."Id" = a."StatusId"
GROUP BY s."Title", a."IsDeleted", a."IsPublic", a."IsClosed"
ORDER BY materials DESC;
```

Не делай вывод `IsPublic = true → бесплатно и разрешено все`. Сначала изучи значения, `ContentSettings`, типы и несколько конкретных материалов. При неизвестной политике материал не допускается в ответы.

### A3. Посмотри текст и набор блоков

```sql
SELECT
    a."Id", a."Title", a."Url",
    length(a."Content"::text) AS main_length,
    count(e."Id") AS blocks,
    sum(length(e."HtmlContent"::text)) AS blocks_length
FROM public."Articles" a
LEFT JOIN public."ArticleEmbedItems" e ON e."ArticleId" = a."Id"
GROUP BY a."Id", a."Title", a."Url", a."Content"
ORDER BY a."Id"
LIMIT 20;

SELECT "Type", count(*) AS blocks
FROM public."ArticleEmbedItems"
GROUP BY "Type"
ORDER BY blocks DESC;
```

Для конкретной статьи скопируй ее UUID и подставь вместо примера:

```sql
SELECT "Id", "Type", "Order", "HtmlContent", "Params"
FROM public."ArticleEmbedItems"
WHERE "ArticleId" = '00000000-0000-0000-0000-000000000000'::uuid
ORDER BY "Order" NULLS LAST, "Id";
```

Последний запрос с нулевым UUID обычно ничего не вернет: его обязательно заменить. Сравни основное поле и блоки: это альтернативные представления, дополнения или дубли? Не склеивай все поля без анализа. Если несколько блоков имеют одинаковый `Order`, порядок по ID только делает экспорт повторяемым; он не доказывает авторскую последовательность.

### A4. Разбери курсы и платные уроки

```sql
SELECT
    c."Id", c."Title", c."Cost", c."Url",
    count(b."Id") AS active_bindings
FROM public."Courses" c
LEFT JOIN public."CourseLessonBindings" b
    ON b."CourseId" = c."Id" AND NOT b."IsDeleted"
GROUP BY c."Id", c."Title", c."Cost", c."Url"
ORDER BY c."Title";

SELECT
    c."Title" AS course,
    l."Id" AS lesson_id, l."Title" AS lesson, l."IsGroup",
    b."IsTrial", b."IsClosed", b."ClosedUntil", b."Order"
FROM public."CourseLessonBindings" b
JOIN public."Courses" c ON c."Id" = b."CourseId"
JOIN public."Lessons" l ON l."Id" = b."LessonId"
WHERE NOT b."IsDeleted" AND NOT l."IsDeleted"
ORDER BY c."Id", b."Order" NULLS LAST, l."Id"
LIMIT 40;
```

`Cost = 0`, `NULL`, `IsTrial`, подписка и доступ к уроку требуют отдельного толкования. Для MVP полные платные уроки не включать в answer-корпус. Публичность описаний курсов тоже нужно подтвердить; наличие описания в backup еще не достаточное основание для внешней передачи.

### A5. Темы и отрасли

Начни с `Topics`, `Tags`, `Industries`, затем `ContentSettings` и трех таблиц связей. Связывай материал по `EntityId` и проверенному `EntityTypeId`; не выдумывай соответствие UUID типа сущности таблице. Сохраняй и ID, и читаемое название темы. Оценки пользователей и персональные поля пока не нужны для MVP.

Результаты этапа: `docs/ai/data_audit.md`, `docs/ai/access_policy.md`. Запиши смысл полей, источники текста, состав URL, неясности и принятое решение по каждому виду материалов. В документации кода не копируй большие фрагменты закрытых текстов.

Готово, когда можешь объяснить, как из одной статьи получается текст с источником, и почему этот текст допустимо использовать в ответе.

## 6. Этап B — экспорт и нормализация корпуса

Текущий пилот реализован в `scripts/prepare_articles.py`. Команды запуска и ручной сверки приведены в [README](../README.md). Структура пакета ниже относится к будущей интеграции с backend.

Где делать: `backend/alfa_ai/data/`, результаты — в `data/local/`. Текст остается локальным.

Подключение из Python на Windows: host `127.0.0.1`, port `5433`, database `alfa_course`, user `alfa`. Из контейнера приложения адрес будет именем сервиса в общей Docker-сети, а не `127.0.0.1`.

В PowerShell задай локальные переменные; пароль здесь — пример, подставить пароль восстановленной БД:

```powershell

$env:PGPORT = '5433'
$env:PGDATABASE = 'alfa_course'
$env:PGUSER = 'alfa'
$env:PGPASSWORD = 'YOUR_EXISTING_DATABASE_PASSWORD'
```

Самостоятельная проверка подключения, которую можно выполнить уже после установки psycopg:

```powershell
@'
import psycopg

with psycopg.connect() as conn:
    conn.read_only = True
    with conn.cursor() as cur:
        cur.execute('SELECT count(*) FROM public."Articles"')
        print(cur.fetchone()[0])

```

Ожидается `855`. Пароль не печатать и не включать в код. Для регулярного ETL желательно отдельное подключение с правами чтения. Не изменяй исходные таблицы ради очистки: преобразования выполняются в экспортированных данных.

### B1. Экспорт

Реализуй `export.py`: прочитать основной материал и его блоки, сохранить их раздельно как промежуточные записи. На первом проходе — 20–30 вручную выбранных материалов, затем весь разрешенный набор.

Используй параметры psycopg `%s` для UUID/значений; не собирай SQL из пользовательского текста. UUID и даты сериализуй явно. Не передавай в выгрузку `UserRatings.IP`, служебные авторские ID и историю реальных пользователей — для содержимого материалов они не нужны.

### B2. Очистка

В `clean.py` реализуй и проверь:

1. Удаление `script`, `style`, комментариев и служебной разметки.
2. Сохранение заголовков, абзацев, пунктов списков, читаемого содержания таблиц.
3. Нормализацию пробелов и переносов, декодирование HTML-сущностей.
4. Сохранение значимых чисел, дат, знаков и налоговых аббревиатур.
5. Разбор `Params` только для типов блоков, смысл которых изучен. Не помещай сырой JSON в текст поиска.
6. Поиск повторов основного текста и блоков; не удаляй повторные короткие определения без разбора.
7. Отчет о пустых/поврежденных материалах с причиной исключения.

Простой `get_text(' ', strip=True)` годится для первого просмотра, но склеивает структуру. Для финального chunking нужно сохранить границы разделов.

### B3. Единая схема документа

Пример будущей нормализованной записи; ID, URL и текст ниже условные:

```json
{
  "document_id": "article:uuid",
  "source_id": "uuid",
  "kind": "article",
  "title": "Название материала",
  "url": null,
  "text": "Очищенный текст",
  "topics": [],
  "industries": [],
  "answer_allowed": false,
  "recommend_allowed": false,
  "external_api_allowed": false,
  "policy_version": "v1",
  "content_hash": "sha256..."
}
```

`false` по умолчанию: значения становятся `true` после применения проверенной политики. `external_api_allowed` — явное решение политики обработки, а не существующий флаг исходной БД. Бесплатность сама по себе не доказывает допустимость передачи внешнему сервису.

Для относительного `Url` не придумывай домен и маршрут. Пока правило не установлено, оставь `url = null`, отметь материал для проверки и не создавай несуществующие ссылки. Логика URL должна быть общей для поиска и рекомендаций.

Для платных материалов формируй отдельную рекомендательную запись только из разрешенных метаданных. Не сохраняй полный урок в скрытом поле payload «на всякий случай».

Готово, когда у каждого документа есть источник, правила доступа, чистый текст и повторяемый ID; повторный экспорт не создает дубли.

## 7. Этап C — chunking

Пилот реализован в `scripts/chunk_articles.py` с бюджетом 350 токенов на полный вход модели. Выход — `data/local/pilot_chunks.jsonl`. Запуск и предпросмотр описаны в [README](../README.md#подготовка-корпуса).

Где делать: `data/chunk.py`; выход — `data/local/chunks.jsonl`.

Для E5-base длинные входы обрезаются до 512 токенов. Поэтому прежний совет «300–600 токенов» слишком широкий: начни примерно с 250–350 токенов тела, учитывая заголовок, название раздела, префикс и специальные токены. Проверяй длину токенизатором самой embedding-модели, а не количеством слов или символов.

Алгоритм первой версии:

1. Разбить документ на разделы и абзацы.
2. Наполнять фрагмент соседними абзацами до токенного бюджета.
3. Слишком длинный абзац делить по предложениям, затем токенам при необходимости.
4. Для длинных разделов попробовать перекрытие 30–50 токенов; коротким определениям оно не нужно.
5. Добавлять заголовок материала и раздела в embedding-текст; полный контекст сохранять в payload.
6. Проверить, что при разбиении не исчезли конец статьи и строки таблиц.

У chunk должны быть `chunk_id`, `document_id`, `chunk_index`, `title`, `section`, `text`, `url`, флаги политики. Для ID подойдет стабильный UUID5 от вида материала, исходного ID, версии chunker и номера фрагмента. В manifest фиксируй hash корпуса, параметры и модель.

Нельзя считать, что 32 475 `ArticleEmbedItems` — уже 32 475 хороших поисковых фрагментов. Один блок может быть пустым, картинкой, длинным разделом или частью таблицы.

Готово, когда первые 30 документов вручную проверены, каждый фрагмент имеет источник и не обрезается моделью.

## 8. Этап D — первый поиск без LLM

Поиск по допущенному корпусу доступен через `alfa-ai`. Метрики отдельных прогонов описаны в [локальной приёмке](ai/LOCAL_ACCEPTANCE.md).

Где делать: `retrieval/embeddings.py`, `index.py`, `search.py`.

### D1. Проверь модель на двух текстах

Небольшой самостоятельный пример; первая загрузка скачивает веса, исходные материалы никуда не отправляются:

```python
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("intfloat/multilingual-e5-base", device="cpu")
texts = [
    "passage: Как выбрать форму регистрации бизнеса: ИП или ООО",
    "passage: Как построить программу удержания клиентов",
]
documents = model.encode(texts, normalize_embeddings=True)
query = model.encode(
    ["query: Хочу открыть свое дело, как зарегистрироваться?"],
    normalize_embeddings=True,
)
print("Размерность:", model.get_sentence_embedding_dimension())
print("Оценки:", (query @ documents.T).tolist())
```

Для E5 префиксы `query: ` и `passage: ` нужны и для русского языка. Один и тот же embedding-текст нельзя префиксировать дважды. Модель загружай один раз на процесс; при смене модели или revision перестраивай индекс. Для начала CPU достаточно проверить на малом корпусе; реальную скорость измерить.

### D2. Первый индекс можно проверить локально

Чтобы сначала разобраться с API, qdrant-client умеет локальный режим. Самостоятельный пример на вымышленных данных, Qdrant-сервер не нужен:

```python
from uuid import NAMESPACE_URL, uuid5

from qdrant_client import QdrantClient, models
from sentence_transformers import SentenceTransformer

model = SentenceTransformer("intfloat/multilingual-e5-base", device="cpu")
client = QdrantClient(":memory:")
name = "learning_example"
texts = ["Регистрация ИП и ООО", "Программа лояльности для покупателей"]
vectors = model.encode(
    ["passage: " + text for text in texts], normalize_embeddings=True
)
client.create_collection(
    collection_name=name,
    vectors_config=models.VectorParams(
        size=model.get_sentence_embedding_dimension(),
        distance=models.Distance.COSINE,
    ),
)
client.upsert(
    collection_name=name,
    points=[
        models.PointStruct(
            id=str(uuid5(NAMESPACE_URL, "example:" + str(i))),
            vector=vector.tolist(),
            payload={"text": text, "answer_allowed": True},
        )
        for i, (text, vector) in enumerate(zip(texts, vectors, strict=True))
    ],
    wait=True,
)
query = model.encode(
    "query: Как зарегистрировать бизнес?", normalize_embeddings=True
)
result = client.query_points(
    collection_name=name,
    query=query.tolist(),
    query_filter=models.Filter(
        must=[models.FieldCondition(
            key="answer_allowed", match=models.MatchValue(value=True)
        )]
    ),
    limit=2,
    with_payload=True,
)
for hit in result.points:
    print(hit.score, hit.payload["text"])
```

Сохрани пример, например, в `backend/experiments/search_demo.py` и выполни из `backend/`:

```powershell
uv run python experiments/search_demo.py
```

Это учебный пример, а не готовый индекс исходной БД. `:memory:` исчезает при завершении процесса. Для реального корпуса используй Docker-сервер с постоянным volume; локальный файловый режим не открывай одновременно из индексатора и бота.

### D3. Сервер для интеграции

Из корня проекта можно отдельно поднять Qdrant. Первый pull используется для выбора образа; затем запуск идет по полученному неизменяемому digest:

```powershell
docker pull qdrant/qdrant:latest
$alfaQdrantImage = docker image inspect qdrant/qdrant:latest --format '{{index .RepoDigests 0}}'
docker run -d --name alfa-qdrant -p 127.0.0.1:6333:6333 -v alfa_qdrant_data:/qdrant/storage $alfaQdrantImage
```

Зафиксируй digest в будущем Compose команды и отчете окружения. Это разовый старт, а не инструкция каждый раз подтягивать `latest`. Если контейнер с таким именем уже существует, не удаляй его: используй `docker start alfa-qdrant` и проверь образ/данные.

Dashboard: `http://localhost:6333/dashboard`. Python-клиент с Windows: `QdrantClient(url="http://127.0.0.1:6333")`. Из контейнера бота — имя сервиса в общей Docker-сети. Финальный Compose объединяет друг, не оставляйте два разных Qdrant на одном порту.

Для реального индекса:

- размерность получать из модели, distance — cosine;
- payload-индексы для часто используемых `answer_allowed`, `external_api_allowed`, `kind`, `document_id` и других фильтров;
- ограничения доступа применять в поиске, не после глобального top-k;
- новый корпус/модель строить в новую collection, не затирая работающую;
- одинаковый набор чанков повторно загружать через стабильные ID без роста количества;
- ограничить и проверить batch size, логировать число документов/чанков, ошибки и время.

Для внешнего LLM-контекста требуются оба фильтра: разрешено для ответа и разрешено для внешней передачи. В runtime перед отправкой проверяй их еще раз. Для рекомендаций используй отдельную collection разрешенных карточек, например `alfa_cards_v1`; для текстовых ответов — `alfa_answers_e5_v1`. Обе — из явно подготовленных корпусов.

Готово, когда `search_materials()` возвращает пять результатов с названиями и источниками, перезапуск сохраняет индекс, закрытые материалы не попадают в выдачу.

## 9. Этап E — проверочный набор и поисковые метрики

Рабочий набор оценки по статьям запускается через `uv run --locked python -m scripts.eval_rag`.

Начни до настройки поиска, не после. Файлы — в `evals/local/`; инфраструктуру проверок и синтетические примеры без контента можно хранить в коде.

Первая версия — 15 вопросов на малом корпусе; затем расширь до 50–100 на полном разрешенном наборе. Это ориентир объема работы, не число, требуемое кейсом.

Каждая строка `retrieval_dev.jsonl`:

```json
{
  "case_id": "q001",
  "query": "Вопрос по проверенному материалу",
  "profile": {},
  "expected_status": "answer",
  "relevant_document_ids": ["article:uuid"],
  "relevant_chunk_ids": [],
  "notes": "Почему этот источник отвечает на вопрос"
}
```

Покрой прямые вопросы, перефразировки, разговорную речь, аббревиатуры, опечатки, неполные сведения, отсутствие ответа, платный контент и продолжение диалога. Правильные источники проверяй чтением; придуманный вопрос без подходящего материала не считается положительным примером.

Раздели development и holdout. Перефразировки одного вопроса не разбрасывай между частями, иначе получишь слишком оптимистичный результат. Holdout не используйте для постоянного выбора chunk size и prompts.

Считать отдельно:

| Метрика | Смысл |
| --- | --- |
| Hit@5 | Доля вопросов, где хотя бы один релевантный документ найден в пятерке |
| Recall@5 | Доля размеченных релевантных документов, найденных в пятерке |
| MRR@5 | Среднее `1 / позиция первого релевантного`, ноль при отсутствии в top-5 |
| Доля нарушений политики | Сколько выдач содержат запрещенный контент |
| latency p50/p95 | Типичное время поиска и медленные запросы |

При нескольких чанках одной статьи сначала убери дубли по `document_id`, если метрика документная. Поисковые метрики считать по положительным вопросам; для `no_answer` и уточнений нужен отдельный отчет о поведении.

Сравни простой лексический baseline (для старта TF-IDF, при необходимости scikit-learn) и dense E5 на одной разметке. TF-IDF не называй BM25. Требование сравнения с baseline относится к треку 1, но тебе такое сравнение полезно как инженерная проверка.

Для каждого прогона сохраняй модель/revision, hash корпуса, chunking, параметры поиска, дату, сырые ранги и сводку. Отдельно измеряй прогретый поиск и время первой загрузки модели.

Готово, когда есть воспроизводимый отчет и список конкретных ошибок. Пример внутренней цели MVP — Hit@5 не ниже 80% на вручную проверенном небольшом holdout; это командный ориентир, не обещание качества и не требование жюри. Запреты доступа должны проходить все подготовленные проверки.

## 10. Этап F — RAG и генерация ответа

Ответы по 30 сверенным фрагментам 13 статей доступны через `alfa-ai`. `scripts/eval_rag.py` сохраняет контекст и цитаты для ручной проверки. [Локальная приёмка](ai/LOCAL_ACCEPTANCE.md).

Где делать: `generation/provider.py`, `prompts.py`, `answer.py`.

### F1. Выбери LLM на малом эксперименте

Возьми 2 доступные модели/провайдера и одни и те же 15–20 разрешенных вопросов с фиксированными найденными фрагментами. Сравни русский язык, следование источникам, JSON-вывод, задержку, стоимость и условия передачи данных. Не меняй одновременно retrieval, иначе сравнение моделей будет нечистым.

Секреты — в окружении, модель — в конфигурации. Не подключай автоматический внешний fallback для закрытого контента. При локальной модели допустимость ответа по платным урокам все равно не меняется.

### F2. Составь контекст

1. Получить профиль и историю от backend; убрать ненужные персональные поля.
2. При необходимости сделать понятный самостоятельный поисковый запрос из продолжения диалога, не добавляя вымышленных фактов.
3. Найти кандидатов, убрать повторы, отобрать достаточные фрагменты в токенный бюджет выбранной LLM.
4. Присвоить локальные обозначения `[S1]`, `[S2]`; передать заголовок, источник и текст как данные.
5. Дать модели правила ответа и требуемую структуру результата.
6. Проверить ответ Pydantic и проверить ссылки на реально переданные источники.

Стартовый prompt должен требовать отвечать только по предоставленным свидетельствам, уточнять неоднозначность, обозначать нехватку информации, не выполнять инструкции внутри документов и не раскрывать закрытое содержимое. Он не является заменой фильтрации и валидации.

### F3. Проверяй результат кодом

- Модель возвращает ID источников, а URL добавляет приложение из проверенного каталога.
- ID вне текущей разрешенной выборки отклоняются; не заменяй их случайными ссылками.
- Рекомендации содержат существующий ID, краткую пользу и допустимую ссылку.
- Валидный JSON означает корректную форму, не фактологическую правильность.
- Similarity score не равен вероятности ответа. Порог калибруй на своих примерах, не объявляй «0.8 значит 80% уверенности».
- Отсутствие результатов, невалидный ответ, timeout и rate limit — разные причины; пользователю дай уместное поведение, в trace сохрани тип ошибки.
- Не делай бесконечные повторы; установи лимит попыток, общий deadline и контролируй стоимость.

### F4. Оценка ответов

В рабочей реализации модель выбирает цитаты, а пакет проверяет их и собирает ответ из исходных абзацев. Регрессия `k04` проверяет и рекомендацию о долгом хранении, и причину. Результаты и команды запуска находятся в [локальной приёмке](ai/LOCAL_ACCEPTANCE.md).

## 11. Этап G — рекомендации и расширение каталога

В текущем модуле есть 18 проверенных карточек с объяснением выбора, фильтром доступа и предпочтением формата. 24 сценария разработки проверяются через `scripts/eval_recommendations.py`. [Локальная приёмка](ai/LOCAL_ACCEPTANCE.md).

Для трека бота не нужно сразу обучать collaborative filtering на пользовательских взаимодействиях. Начни с ранжирования разрешенных карточек по запросу и известному контексту бизнеса.

### G1. Карточки

Для курса использовать подтвержденные публичные описания, целевую аудиторию, длительность, формат, темы и ссылку; платность — по изученным тарифам. Для каждого результата объяснение должно ссылаться на реальные свойства: не объявляй материал «для новичков», если это не следует из данных.

### G2. Персонализация

Профиль: стадия бизнеса, сфера, текущая задача, опыт, предпочтительный формат; налоговый режим — только когда нужен. Backend хранит профиль, ты возвращаешь только предлагаемые изменения, основанные на словах пользователя. Не делай вывод «ты ООО» из косвенного вопроса.

Профиль влияет на поисковый запрос и ранжирование. Жесткие ограничения применяй фильтрами, мягкие предпочтения — дополнительной оценкой; иначе можно случайно исключить все полезные материалы. При пустом профиле бот все равно должен отвечать.

### G3. Остальные типы

| Тип | Первая реализация |
| --- | --- |
| Статьи и глоссарий | Проверенный разрешенный полный текст |
| Документы и шаблоны | Описание и доступные текстовые блоки; наличие файла проверить |
| Курсы | Разрешенные карточки для рекомендаций |
| Платные уроки | Полный текст не попадает в ответы; только допустимые метаданные |
| Подкасты | Название и проверенная ссылка для рекомендаций. При наличии разрешённой расшифровки поиск возвращает фрагмент и интервал записи. |
| Вебинары | Описание и метаданные; запись не считать расшифрованной |
| Калькуляторы | Назначение и ссылка; реальный расчет только после отдельной реализации проверенной функции |

Подкаст из описания можно рекомендовать, но нельзя приписывать ему тезисы, которых нет в описании. Расшифровка аудио — дополнительный этап после проверки доступа к файлам и разрешений; таймкоды возвращаются только из реальной расшифровки.

Готово, когда бот предлагает уместные бесплатные и платные материалы, объясняет выбор и не подменяет консультацию навязчивой продажей.

## 12. Этап H — диалог и намерения напоминаний

Реализованы явно сказанные изменения профиля, продолжение с переданным предыдущим вопросом и предложения создания, изменения и отмены напоминаний. Поддерживаемые формулировки и способы проверки описаны в [локальной приёмке](ai/LOCAL_ACCEPTANCE.md).

Где делать: `dialogue/profile.py`, `intents.py`, общие `contracts.py`.

Выдели категории: вопрос, запрос рекомендаций, уточнение профиля, создание/изменение/отмена напоминания, продолжение сценария. На старте можно сочетать явные команды и структурированный LLM-вывод; отдельный обучаемый классификатор не обязателен.

Будущий результат извлечения намерения:

```json
{
  "action": "create_reminder",
  "subject": "Продолжить обучение",
  "local_datetime": null,
  "timezone": null,
  "recurrence": null,
  "missing_fields": ["time", "timezone"],
  "needs_confirmation": true
}
```

Правила:

- В запрос передаются текущие дата/время и известный часовой пояс пользователя. Не зашивай «сегодня» и Москву в prompt.
- «Завтра вечером» требует уточнения времени или явного согласованного правила; часовой пояс нельзя угадывать по языку.
- «Раз в месяц 31-го» требует определенной политики коротких месяцев, «по будням» — определенной трактовки рабочих дней.
- Налоговый режим и категория бизнеса не дают права выдумать актуальный срок налога. Для MVP можно напомнить в явно заданную пользователем дату; вычисление официального срока требует отдельного проверенного источника и правил.
- Для изменения/отмены backend проверяет владельца задания. При нескольких совпадениях бот просит выбрать, а не отменяет все.
- Твой модуль возвращает предложение; backend сохраняет, подтверждает результат и обеспечивает доставку. Бот не говорит «создано», если сохранение не удалось.
- Повторная обработка одного сообщения не создает два задания; backend получает ключ идемпотентности и отвечает фактическим статусом.

Готово, когда вы вдвоем проходите: уточнение → подтверждение → сохранение → отправка → изменение повторения → отмена, включая перезапуск worker.

## 13. Этап I — интеграция с Telegram и виджетами

Порядок работы обновлён по решению владельца AI/ML: сначала локальная приёмка всего модуля, затем подключение к Telegram. Приёмка выполняется через CLI и Python API.

Устанавливаемый пакет `src/alfa_ai/` предоставляет `AIService.answer()`, обработку отмены, таймаутов и перегрузки, а также CLI `alfa-ai`. Контракты `AIRequest` и `AIResponse` поддерживают краткий профиль, предыдущий запрос, карточки материалов и предложение напоминания. Пакет подключается к backend как зависимость после локальной приёмки. [Инструкция интеграции](ai/INTEGRATION.md).

Для вызова из aiogram учтите: локальный расчет embeddings синхронный и может блокировать event loop. Вынесите его в ограниченный executor/очередь или отдельный процесс при измеренной необходимости; не запускайте неограниченно по потоку на каждое сообщение. LLM API вызывается асинхронно, параллелизм ограничен.

Держи модели и клиент Qdrant долгоживущими. Проверяй время ожидания, отмену запроса, отсутствие индекса и поведение при недоступности провайдера. Не храните приватный диалог в общей глобальной истории.

Виджеты — задача интерфейса: AI возвращает карточки, шаги и параметры, backend/шаблон их рисует. Произвольный HTML/JavaScript из LLM не требуется. Основной сценарий должен работать текстом и кнопками; отсутствие поддержки виджетов не блокирует ответы и напоминания.

## 14. Этап J — воспроизводимость и подготовка защиты

### Целевой CLI

Ниже названия команд, которые нужно реализовать в `alfa_ai/cli.py`; сейчас это спецификация, не существующие команды. Все пути считаются от `backend/`:

```powershell
uv run python -m alfa_ai.cli export --output ../data/local/raw.jsonl
uv run python -m alfa_ai.cli prepare --input ../data/local/raw.jsonl --output ../data/local/documents.jsonl
uv run python -m alfa_ai.cli chunk --input ../data/local/documents.jsonl --output ../data/local/chunks.jsonl
uv run python -m alfa_ai.cli index --input ../data/local/chunks.jsonl
uv run python -m alfa_ai.cli search --query 'Как зарегистрировать бизнес?'
uv run python -m alfa_ai.cli eval-retrieval --cases ../evals/local/retrieval_dev.jsonl
uv run python -m alfa_ai.cli ask --query 'Как зарегистрировать бизнес?'
```

`prepare` не должен молча разрешать неизвестные материалы: принимает утвержденную версию политики или локальный список проверенных ID. `index` не должен незаметно удалять текущую collection. При отсутствии файла, настроек или политики команда завершается понятной ошибкой.

### Что фиксировать

- `uv.lock`, версия Python, digest Docker-образа Qdrant.
- ID embedding-модели и конкретный revision, размерность и preprocessing.
- ID/версия LLM, prompt version, параметры генерации.
- Версия политики доступа, ETL/chunker, hash корпуса и количество документов/чанков.
- Время индексации, объем индекса, cold/warm latency, токены и стоимость ответа.
- Пройденные сценарии, провалы и известные ограничения.

Не печатай в общие логи секреты, полный закрытый контекст и личные диалоги. Для отладки достаточно trace ID, разрешенных ID источников, времени шагов и типа ошибки. Локальные подробные трассы тоже являются производными данными и не публикуются автоматически.

### Минимальные проверки

| Проверка | Ожидаемый результат |
| --- | --- |
| Повторный ETL/index | Нет дублей, одинаковый результат при той же конфигурации |
| Chunking длинной статьи | Конец не потерян, токенный лимит соблюден |
| Поиск с фильтром | Закрытый материал не попадает в answer-контекст |
| Невалидный ID/URL модели | Отклоняется; приложение не создает новую ссылку |
| Неизвестная тема | Нет уверенного выдуманного ответа |
| Неоднозначный вопрос | Уместное уточнение |
| Пустой профиль | Полезный основной сценарий без длинной анкеты |
| Два пользователя | Нет смешивания профилей и истории |
| LLM timeout / Qdrant недоступен | Понятная ошибка без ложного подтверждения действия |
| Напоминание | Есть факт сохранения и доставки, изменение и отмена |

Тесты подготовки данных и схем запускаются без скачивания модели и внешнего API. Интеграционные и платные проверки включаются отдельно. Не ограничивайся тестом «метод вернул непустую строку».

Команды после реализации тестов:

```powershell
uv run ruff check .
uv run ruff format --check .
uv run pytest tests/ai
```

### Материалы для защиты

Подготовь один слайд архитектуры, таблицу baseline/dense/улучшений на одинаковом наборе, 3 удачных диалога и 2 честных ограничения. Покажи, откуда взялся ответ и почему можно рекомендовать платный курс без раскрытия урока.

Для бизнес-эффекта предложи A/B-проверку конверсии в покупку и активных дней на платформе. Переходы по ссылкам и оценки ответа — дополнительные показатели, отключения уведомлений — защитный показатель. Реальный рост конверсии не доказан качеством поиска или синтетическим демо.

## 15. В какой последовательности работать

Оценки времени ориентировочные при уверенном Python и доступе к API. Если опыта мало, этап может занять несколько дней; двигайся по результату, а не по календарю.

| Сессия | Работа | Проверяемый результат |
| --- | --- | --- |
| 1 | Договор с другом, аудит данных и доступа | Контракт, отчет о полях и 20–30 проверенных материалов |
| 2 | ETL и chunking | Чистые документы/чанки, 15 вопросов с источниками |
| 3 | E5 и Qdrant | Консольный top-5 и первый отчет качества |
| 4 | Расширение корпуса и разметки | 50–100 кейсов по возможности, baseline и список ошибок |
| 5 | LLM и ответы со ссылками | `answer()`, уточнения, `no_answer`, проверка политики |
| 6 | Рекомендации и профиль | Карточки бесплатных/платных материалов, персонализация |
| 7 | Намерения напоминаний и интеграция | Сквозной сценарий с backend и реальной доставкой |
| 8 | Оптимизация и защита | Фиксированный запуск, отчет, демонстрация |

Интеграцию контракта начинайте с первой сессии, не откладывайте до седьмой. Сессия 7 — завершение сквозных сценариев, а не первое знакомство с кодом бота.

Если времени мало: разрешенные статьи + глоссарий → dense-поиск → ответы с источниками → простые карточки курсов → профиль → намерения напоминаний и проверка вместе с другом. Напоминания обязательны для трека, поэтому backend разрабатывает их параллельно.

## 16. Что учить и когда

| Когда | Материал | Что сделать после чтения |
| --- | --- | --- |
| Перед ETL | SQL JOIN, psycopg, HTML parsing | Собрать одну статью из БД без изменения оригинала |
| Перед chunking | Токенизация, ограничения E5 | Проверить длины и отсутствие обрезания |
| Перед поиском | Embeddings, cosine similarity, Qdrant points/payload | Получить top-5 и применить фильтр |
| Перед улучшениями | Hit/Recall/MRR, baseline, holdout | Получить честный отчет и список ошибок |
| Перед генерацией | RAG, сообщения LLM, context budget, structured output | Ответить по фрагментам с валидными ID |
| Перед интеграцией | Async Python, ошибки API, идемпотентность | Не блокировать бота и не дублировать действия |

Источники для изучения:

- [Hugging Face LLM Course](https://huggingface.co/learn/llm-course/chapter1/1) — основы моделей и токенизации. Не требуется проходить весь курс до начала работы.
- [uv: проекты](https://docs.astral.sh/uv/guides/projects/) — окружение и lockfile.
- [psycopg: базовое использование](https://www.psycopg.org/psycopg3/docs/basic/usage.html) — чтение PostgreSQL.
- [Карточка multilingual-e5-base](https://huggingface.co/intfloat/multilingual-e5-base) — правильные входы и ограничения модели.
- [Sentence Transformers: поиск и reranking](https://www.sbert.net/examples/sentence_transformer/applications/retrieve_rerank/README.html) — разница retrieval/reranking.
- [Qdrant Quickstart](https://qdrant.tech/documentation/quickstart/) и [Python client](https://github.com/qdrant/qdrant-client) — коллекции и запросы.
- [Qdrant: фильтры](https://qdrant.tech/documentation/search/filtering/) — ограничения выдачи.
- [Qdrant: гибридный поиск](https://qdrant.tech/documentation/hybrid-queries/) — следующий эксперимент при ошибках dense-поиска.
- [Pydantic AI: структурированный вывод](https://pydantic.dev/docs/ai/core-concepts/output/) — типизированный результат, если выберете этот слой.
- [Pydantic Evals](https://pydantic.dev/docs/ai/evals/evals/) — возможная инфраструктура проверок, необязательная для первых JSONL-прогонов.

Позже, только при измеренной необходимости: multilingual reranker, hybrid/RRF, обучение ранжирования, fine-tuning, ASR подкастов, сложная агентная оркестрация. На старте не нужны обучение Transformer с нуля, несколько автономных агентов, Kubernetes и отдельная микросервисная платформа.

## 17. Как понимать, что твоя часть завершена

- Из исходного backup воспроизводимо получается разрешенный корпус, а из него — индекс.
- Поиск работает на реальных вопросах и имеет измеренное качество.
- Ответы опираются на существующие источники, уточняют неоднозначность и честно сообщают о недостатке данных.
- Доступ к платным и закрытым текстам контролируется до внешнего вызова и до вывода.
- Рекомендации используют существующие материалы и объясняют пользу без выдуманных свойств.
- Профиль улучшает ответы, но не обязателен для старта.
- Извлечение намерений согласовано с backend; напоминания реально создаются, меняются, отключаются и доставляются.
- Друг может подключить AI-модуль без копирования ноутбука и ручного редактирования путей.
- Модели, данные, параметры, ограничения и результаты проверки задокументированы.
- Общий основной сценарий запускается по инструкции и проходит демонстрацию.
